## What each kind of constraint guarantees (with this schema's examples)

| Kind | Guarantees | Example here | Evidence of rejection |
|---|---|---|---|
| PRIMARY KEY | unique AND not null; the identifier other tables reference; one per table | `pk_watchlist_items (watchlist_id, instrument_id)` | `03_constraints.out`: duplicate RELIANCE in arjun Long Term → 23505 |
| UNIQUE | no two rows share the value combination (an alternate/candidate key); several per table | `uq_instruments_exchange_symbol (exchange, symbol)` | duplicate NSE RELIANCE → 23505; BSE RELIANCE accepted |
| FOREIGN KEY | the value must exist as a key in the parent table; ON DELETE says what happens to children | `fk_watchlists_user` | watchlist for user 999 → 23503; delete RELIANCE → 23001 (RESTRICT) |
| CHECK | a row-level condition must be true | `ck_alert_rules_direction` (ABOVE/BELOW) | 'SIDEWAYS' → 23514 |
| NOT NULL | a value must be present | `users.email` | NULL email → 23502 |

A PRIMARY KEY is UNIQUE + NOT NULL and is the target of foreign keys. A UNIQUE constraint on NOT NULL columns is an alternate candidate key (all UNIQUE columns here are NOT NULL). NOT NULL is a column property that also decides participation: a NOT NULL foreign key means the child must have a parent (total participation in the ER diagram).
